# 版本与发布制度

本文件是项目版本决策、构建、验收和发布的统一入口。产物目录的细则见 [release/AGENTS.md](../release/AGENTS.md)，每次交付填写 [验收与发布清单](release-checklist.md)。制度适用于后续版本；历史包、指纹和验收记录保留原貌，发现错误时追加更正。

## 什么时候发新版

没有固定日历。新版本应对应一组明确、值得交付的变化：已确认缺陷修复、可用的新能力、兼容性调整或必要的安全修复。内部重构、普通文档修改可随下一次交付合并，不要求每次修改都打包升版。

版本决策由项目负责人确认，执行者负责同步、构建和验收。已确认版本及平台后，普通工程细节连续执行；构建授权不等于上传发布授权。不得自动提交、打标签、推送、上传或更换用户已安装的加载项。

| 变化 | 升版规则 | 示例 |
|---|---|---|
| 修复缺陷、兼容性修补，不破坏现有工具契约或产品行为 | PATCH | `2.2.0 → 2.2.1` |
| 增加向后兼容的工具、能力或产品功能 | MINOR，PATCH 归零 | `2.2.1 → 2.3.0` |
| 删除/改名工具、移除参数、改变已有参数含义或其他不兼容行为 | MAJOR，MINOR/PATCH 归零；列出迁移影响 | `2.3.0 → 3.0.0` |

多种变化合并时采用最高级别。不能只因为改动文件多就升 MAJOR，也不能把破坏兼容的变化按 PATCH 发布。

## 版本号与变更记录

`package.json.version` 是唯一基准。目前支持 `MAJOR.MINOR.PATCH` 三段稳定格式，候选身份另用证据目录标识，例如 `2.2.1-candidate-01`；该目录名不写入产品版本。预发布版本需先确定 Office 清单四段数字的映射，不能直接塞入 `-beta`。

升版时一起更新下列声明，然后运行 `npm run check:version`：

- `package-lock.json` 的顶层版本及 `packages[""].version`。
- `src/bridge/runtime.ts` 的 `VERSION`。
- `wps-addon/src/shared.js`、`office-addon/src/state.js` 的 `ADDON_VERSION`。
- `wps-addon/manifest.xml` 的三段版本；`office-addon/excel/manifest.xml` 的 `MAJOR.MINOR.PATCH.0`。
- `src/renderer/App.tsx`、`LiveWorkspaceCard.tsx`、`SettingsDrawer.tsx` 的版本默认值。
- `CHANGELOG.md` 中对应版本的唯一条目，记录实际变更、兼容影响和验收限制。

未归入版本的变化先写 `Unreleased`；确定交付范围后移入版本条目，避免同一项重复归属。版本条目存在、写有日期或已有本地包，都不表示正式发布；发布状态以验收清单和远端附件记录为准。

加载项部署入口是生成物，升版后通过 `npm run build:addons` 重建，不手改版本。只读版本检查不扫描历史证据或旧包，不替代生成物和最终包验证。

## 候选、验收与正式发布

| 状态 | 条件与允许操作 |
|---|---|
| 开发中 | 源码变化尚在归集；不承诺验收结果。 |
| 候选包 | 已确定目标版本及平台，可重复构建；临时包放系统临时目录或 `dist/`。允许工作区未提交，但必须保存固定提交锚点、差异、未跟踪源码和指纹。 |
| 已验收待发布 | 最终包及适用验收门槛通过，缺陷/限制明确；准备发布说明、固定源码提交与包指纹供负责人审阅。若运行代码变化，必须重建并重验受影响项。 |
| 正式发布 | 负责人明确授权发布；固定源码提交和 `v<版本>` 标签，上传经过验收的同一份包，远端附件哈希对账通过并记录发布地址/时间。 |

**已正式发布的版本冻结**。不能覆盖附件、移动标签或悄悄替换同版本包。发现问题用下一补丁版本修复；单纯补充说明可以追加，不改写当时的验收事实。仅本地、尚未正式发布的同版本包允许替换，替换前保留原指纹及对应证据；不先删旧包再开始构建。

正式发布前，工作区中的交付源码须归入固定提交，候选源码/构建输入与该提交核对一致。记录完整 SHA，不能只写会变化的 `HEAD`。若提交过程中改变了构建输入，重建受影响包。不可用“提交 + 未保存的本地修改”作为正式版本来源。

## 每个版本生成什么包

| 平台 | 本地保留产物 | 公开交付形式 | 保护和签名口径 |
|---|---|---|---|
| macOS arm64 | `release/<版本>/mac/mac-arm64/字浮 CharFloat.app` | 从验收通过的同一 `.app` 制作 ZIP 上传；传输 ZIP 可临时存放，留存其 SHA-256 | Electron 字节码 CLI；默认无开发者证书签名、未公证，不能把 linker ad-hoc 标记描述为开发者签名 |
| Windows x64 | `release/<版本>/win/字浮-CharFloat-<版本>-win-x64.zip` | 同一便携 ZIP | 当前跨平台构建使用 minify CLI 回退；不得宣称与 mac 字节码保护等同，签名状态以实测为准 |

不默认增加 x64 Mac、arm64 Windows、NSIS 安装器或新签名路线。改变平台、安装方式、保护策略或签名方式属于新的交付决策。每个正式版本只保留一套产物；保留旧版本，不为每次修改创建 `rebuild-*` 等旁支目录。

构建使用发布副本 `dist/release-app/`，不改业务源码来保护代码。当前两平台 `beforePack` 会增删共享副本中的 CLI 回退文件，所以正式验收构建必须**串行**，两平台用不同输出目录。现有 `dist:all` / `dist:fast` 并行入口在副本隔离完成前不作为正式验收路径。

推荐先 `npm run build:release && npm run build:win-icon`，再分别调用本地 `electron-builder`，指定独立临时 `directories.output` 和 `--publish never`：mac 使用 `--mac --arm64`，无证书构建使用 `CSC_IDENTITY_AUTO_DISCOVERY=false` 及 `-c.mac.identity=null`；Windows 使用 `--win --x64`。前一进程退出并完成保护检查后再开始后一平台。全部验证通过才整理入 `release/<版本>/`，避免直接打包覆盖已保留的实物。

## 放行门槛

每次交付按变更范围勾选 [清单](release-checklist.md)，不适用项说明理由。以下证据分开记录，不能相互替代：

1. **源码检查**：版本、导航、品牌、能力声明、类型检查及适用单元/契约回归通过；标准版本交付执行完整构建和 `npm test`。
2. **最终包检查**：构建进程退出为零；对实际 `.app` / ZIP 运行 `npm run check:release -- <实际路径>`，核查架构、版本、签名、ASAR/unpacked、运行文件及 SHA-256。检查默认发现范围不等于覆盖所有包，必须显式指定实际产物。
3. **运行时检查**：隔离运行包内真实 CLI、确认字节码/回退路线和 MCP 完整契约；改过桌面启动、安装或更新时验证对应流程。
4. **真实宿主检查**：改过宿主实现、加载项构建/保护/安装、参数转发、文件导出时，对受影响平台使用实际交付的加载项和 CLI 验证，读回写入；涉及持久化时保存、关闭、重开。开发产物通过不能代表发布保护产物通过。
5. **交付审阅**：来源、范围、证据、未通过/未覆盖项以及回退方法齐全；获得明确发布授权后才能上传。

无法完成某平台实机验收时，候选包可以交付试用，但该平台必须标为“未验收”。若要带限制正式发布，由负责人明确接受该缺口并写入发布说明；执行者不得自行把未验收项判为通过。

自动门禁覆盖版本一致性：本地 `prebuild`、打包 `beforePack` 以及双平台 CI 都会检查；错误返回非零。其余已有构建/保护检查继续执行。发布授权、真实宿主验收和历史版本冻结目前由制度与清单约束，没有自动上传/放行程序。

## 证据、上传与回退

证据存 `docs/acceptance/<候选标识>/`，至少记录固定源码 SHA、版本、候选身份、构建输入指纹、工具契约快照、环境/架构、命令与退出码、测试结果、包路径和哈希、已知限制、发布状态。使用仓库相对路径，禁止写凭据或用户文档正文。执行清单随证据进入版本控制；`release/` 已忽略，不能作为唯一记录来源。

上传后记录 Release URL、标签、完整提交 SHA、附件名、大小、本地 SHA-256 与远端 `digest`，逐项核对；mac 对账对象是上传 ZIP，同时记录其来源 `.app` 的关键文件哈希。只保存 `.app` 的哈希不能替代 ZIP 对账。

正式版本故障时，可停止推荐该版、恢复已保留的上一版并发下一补丁版；涉及配置/加载项升级先核对兼容与备份，不自动降级或删除用户文件。旧包清理仍须先列清单、大小、指纹、文档引用并取得授权，保留来源和清理说明。
