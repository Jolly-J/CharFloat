# 当前版本与发包管理核对

核对日期：2026-10-12。本文件区分已有约定、已执行改动与尚未实施的改进，不把建议写成已有程序能力。

## 已有约定与程序

- `CHANGELOG.md` 声明采用 Keep a Changelog 和 Semantic Versioning，已有 Unreleased、2.2.0、2.1.0 记录。
- Git 保存源码历史，本地已有 `v2.2.0` 标签；标签、变更记录和构建产物是不同层面的信息。
- `package.json` 指定当前应用版本、两平台目标、文件白名单、解包资源和构建钩子。
- 产物口径已固定：macOS arm64 可直接运行的 `.app`；Windows x64 免安装 ZIP。每版本一套，目录为 `release/<版本>/{mac,win}`。
- 发布副本、包内资源、代码保护、构建输入是否过期和产物 SHA-256 有脚本检查。现有 CI 执行导航、能力声明、类型、构建、测试及 Windows 脚本；不自动打包或创建 GitHub Release。

## 尚未形成程序护栏的部分

1. 没有统一的升版命令或单一版本来源。版本在 package、锁文件、Bridge、两类加载项运行时、两类清单和界面兜底中分别维护；本次核对前锁文件根版本仍为 2.1.0，其他运行版本为 2.2.0。
2. 没有自动决定发版时间的程序。SemVer 给出变更类别，什么时候完成一批改动并发布仍由产品负责人决定；不会因任意一次代码修改自动升版。
3. 没有将未发布候选、已公开正式版和源码标签冻结组合成一个发布状态机。当前同版本覆盖本地构建的习惯，需要与已公开版本不可改写的 SemVer 约定区分。
4. Unreleased 中仍有较早的品牌/侧栏记录；不能仅凭所在章节断定全部都是这次新增。本次仅新增明确属于 2.2.1 的条目，保留其他历史记录。
5. 双平台并行脚本共用 `dist/release-app`；Windows 钩子增加明文兜底，mac 钩子删除它，存在共享目录变更的潜在竞态。本次用串行平台构建规避，未顺手改造整个构建器。
6. “包构建与内容检查通过”不等于全部真实宿主可用；Windows WPS 的本次实际运行仍缺证据，已有图表标题等问题另列。

## 建议后续固化的发布流程（尚未自动化）

版本仍由人决定发布，但机械一致性不应靠记忆：以 package.json 为权威，提供同步其他运行常量/清单及只读检查命令；构建前拒绝版本漂移。候选构建可重跑，正式发布必须绑定固定源码标签和文件哈希，不替换同版本的公开附件。

按已声明的 [SemVer](https://semver.org/lang/zh-CN/)：兼容修复升 PATCH、兼容功能增加升 MINOR、不兼容接口变更升 MAJOR。内部重构可随一批已验改动交付，不要求每次小调整独立发版；本次有导出兼容修复且工具契约保持，因此选 2.2.1。

一次正式发布应在需要交付的一批改动完成后进行：更新变更记录 → 同步版本 → 静态/构建/回归 → 包内容与实际平台验收 → 固定提交和标签 → 用户决定公开发布 → 对账远端附件。当前构建任务只做到本地包与检查，不宣称这些后续程序已经存在。
