一、桩测试方法（脚本自己就是"桩"，可复核、可重跑）
--------------------------------------------------------------------------------
把加载项入口 taskpane.js 放进 Node 的 vm 上下文执行，用记录型桩替换宿主环境：
  · `Office`：onReady / HostType.Excel / context.document.url 桩；
  · `Excel.run(cb)`：进桩时记录 `Excel.run`，把 `context` 换成**记录代理**——它的每次
    属性访问与调用都按出现顺序进记录（如 `CALL context.workbook.worksheets.getItem("Sheet1")`），
    返回可继续链式访问的同源桩；`then` 特判为 undefined，避免 await 把桩当 thenable；
  · `WebSocket`：进桩时记录注册包，`send()` 收进数组供取回 rpc_response；
  · `document` / `setTimeout` / `Math.random`：安全桩 + 固定随机数，保证可重现。
每条 RPC 的做法：**清空记录 → 投递一条 `{id, method, params}` → 让事件循环跑完 →
取该条的调用序列与 rpc_response**。同样参数分别喂给改造前/改造后文件，逐行比对。
（20 条 RPC 的名单与参数见脚本内 SNAPSHOT_METHODS / COMMON_PARAMS。）

  说明（如实登记）：P3.3 当时所用的那份"20 条名单"没有随证据一起留档，本次是**按脚本内
  固定名单重建**的 20 条（覆盖读 / 写 / 脚本 / 图表 / 表格 / 批注 / 预览等域）。名单本身
  不影响结论——结论是"同一名单、同一参数下改造前后逐行一致"；为了不止步于 20 条，
  下面 §三 另附**全部 77 个分支**的扩展跑，同样 77/77 一致。
