## 图标问题第二轮：条目数不足（结论不完整，未解决）

第一版即使 rcedit 成功执行，Windows 上**仍看不到应用图标**。用 `resedit` 直接读 exe 资源发现：

| | RT_GROUP_ICON 条目 | 尺寸 |
|---|---|---|
| 原版 Electron exe（对照） | 4 条 | 16 / 32 / 48 / 256 |
| 第一版产物 | **1 条** | 仅 256 |

原因：electron-builder 从 `build/icon.png` 自动生成的 `.icon-ico/icon.ico` **只有一个 256px 条目**；Windows 资源管理器的小图标视图按尺寸查找条目，找不到 16/32/48 就显示空白图标。

修复：
1. 新增 `scripts/build-win-icon.mjs`（`npm run build:win-icon`），用 macOS `sips` 把 `build/icon.png` 缩成 16/24/32/48/64/128/256 七种尺寸并按 ICO 规范拼装（PNG 内嵌）→ 产出 `build/icon.ico`（7 条目，66924 字节）。
2. `package.json` 的 `build.win.icon` 指向 `build/icon.ico`，不再让 electron-builder 自动生成。
3. 重新打包（rcedit 正常执行）。

**修复后实测**：exe 内 `RT_GROUP_ICON` **7 条**（16/24/32/48/64/128/256），`RT_ICON` 资源 7 个；版本信息 `Office Agent Bridge` 命中 ✅。

最终 SHA-256：x64 `4c4adbaaead4f205ca7c5df3fe2f676081381cac104572cab4c4ad5afacc8b48`；arm64 `8a1bab9e540ab5c774340a8d2e2fc2a040597e1c90c0b80208aa29145e9b3ac4`。

> ⚠️ **这一轮的结论有误，已被第三轮推翻**：当时只校验了"条目数 = 7"，用户实机复测**仍然没有图标**。条目数量正确 **不等于** 条目格式可用——见下节。

> 校验方法提醒：**PE 版本资源是 UTF-16LE**，`strings -a`（只找 ASCII）会漏判；应用 `Buffer.indexOf(Buffer.from(s,'utf16le'))` 或 `resedit` 读取资源表。

## 图标问题第三轮：条目**编码格式**错误 + PE 长度字段截断（已修复）

使用者实机复测第二轮产物：exe 文件图标**仍然空白**（应用内图标正常）。这一轮不再只看条目数量，改为逐条比对**编码格式**，并与**原版 `electron.exe`** 做对照。

### 根因 1：小于 256×256 的条目用了 PNG 内嵌

| 尺寸 | 原版 `electron.exe`（Windows 上显示正常） | 第二轮产物（空白） |
|---|---|---|
| 16×16 | DIB(BMP) 1320B | PNG 732B |
| 32×32 | DIB(BMP) 5160B | PNG 1834B |
| 48×48 | DIB(BMP) 11560B | PNG 3237B |
| 256×256 | PNG 18963B | PNG 40753B |

Windows 只对 **256×256** 支持 PNG 内嵌条目，更小的尺寸必须是 BMP(DIB)；全部用 PNG 时资源管理器的小/中/大图标视图取不到可解码的条目。原版 Electron 正是"小尺寸 DIB + 256 PNG"的结构。

### 根因 2：128×128 的 DIB 超过 64KB，PE 组目录长度被截断

修完根因 1 后先按 128px DIB（67624 字节）生成，实测 exe 的 `RT_GROUP_ICON` 中该条目 `dwBytesInRes` 变成了 **2088 = 0x0828**（正确值 0x10828 的低 16 位）——electron-builder 经 rcedit 写 PE 资源时把该字段截断成 16 位。资源本体完整（`RT_ICON` 仍是 67624 字节），但组目录长度错误，Windows 按该长度解析拿不到这张图。

- 复现/核验：`node docs/acceptance/2.1.0-p0p1/p5/inspect-pe-icons.mjs <exe>`，再与 `build/icon.ico` 目录项里的 67624 对照
- 处理：尺寸集合去掉 128（改用 96×96，DIB 38056 字节），并给生成器加硬上限——任何条目超过 65535 字节直接报错，不落盘

### 修复内容

1. [build-win-icon.mjs](../../../../scripts/build-win-icon.mjs) 重写为**纯 Node**（自带 PNG 解码 / 面积平均缩放 / PNG 编码 / DIB 封装），不再依赖 macOS `sips`：
   - `< 256` 写 32bpp DIB（`BITMAPINFOHEADER` 40 字节 + 自下而上 BGRA + 1bpp 4 字节对齐 AND 掩码）
   - `256` 写 PNG 内嵌
   - 尺寸集合 `16/24/32/48/64/96/256`
   - 写完调用 `verifyIco()` 自检（条目数、编码格式、DIB 头、64KB 上限），**不通过不落盘**
2. `npm run dist` 串联 `build:win-icon`，避免新克隆或新主机上静默退回 electron-builder 自动生成的单条目 ICO
3. 新增回归测试 [win-icon.test.ts](../../../../tests/win-icon.test.ts)（10 项断言，含"<256 必须是 DIB"与">64KB 必须报错"两个回归项）
4. 新增只读核验脚本 [inspect-pe-icons.mjs](inspect-pe-icons.mjs)

### 验证（静态 + 构建级，**不是**实机验收）

- 两个架构的 exe 实测：`RT_GROUP_ICON` 7 条目，`<256` 全为 DIB（`biSize=40`、`biHeight=2×宽`、`bpp=32`），`256` 为 PNG；**组目录长度与资源实际长度逐条一致，无截断**
